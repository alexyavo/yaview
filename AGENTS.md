## Customizations on `main`

- Vim-style `h`/`l` horizontal scrolling in `pdf_viewer/keys.config`, using mode-prefixed bindings (first matching mode wins; `t` = text selected, `r` = visual mark/ruler mode). `h` still adds a highlight when text is selected. `l` still runs `overview_definition` in ruler mode.
- `ss` (`external_search` + `s`) searches selected text on Kagi in the default browser. Google Scholar moved to `sc`. Both `pdf_viewer/prefs.config` and the hardcoded defaults in `pdf_viewer/main.cpp` were changed.
- `o` opens the embedded in-app file browser rooted at the current document's folder (`open_document_embedded_from_current_path`). `Ctrl+o` opens it at `default_open_file_path`, and `Ctrl+Shift+o` opens the native macOS dialog. `FileSelector` in `pdf_viewer/ui.h` now starts in the home folder when given no path, instead of the process working directory (`/` for Finder launches).
- All visible search matches are highlighted, not just the current one (`should_highlight_unselected_search`, enabled in `prefs.config` and `config.cpp`).
- `Ctrl+D` / `Ctrl+U` run `screen_down` / `screen_up`, like PageDown/PageUp. On macOS `<C-...>` in keys.config is the physical Ctrl key and `<D-...>` is Cmd. The user asked for Ctrl, not Cmd.
- Tab bar: `MainWidget::tab_bar` (a `QTabBar`) lists `document_manager->get_tabs()`. Every opened document joins that list; `DocumentManager::add_tab_after` puts a newly opened document's tab right after the current one, like browsers (session restore keeps the saved order). The bar floats over the top edge of the view, like the status bar at the bottom, because mouse handling uses main-window coordinates with no offset correction; putting it in the layout would shift every click. `update_all_tab_bars()` must run after any `add_tab`/`remove_tab`.
- Tab bar structure and stacking: `tab_strip` (themed background; pressing it drags the window, double clicking zooms) under `tab_scroll_area` (a `QScrollArea` holding `tab_bar`, which is as wide as all its tabs). Stacking order: document view, tab strip, tab scroll area, popups, status bar. `set_current_widget` stacks popups directly under `status_label`, so the tab widgets stay under `status_label` and are never raised; raising them drew them over the command palette and table of contents. Restored tabs from a previous session refresh the bar in `open_tabs`.
- In every list popup (table of contents `t`, command palette, file browser, ...), Ctrl+N / Ctrl+P move one line down / up and Ctrl+D / Ctrl+U one page down / up. Tab moves down and Shift+Tab up, except in the file browser, where Tab completes the typed path with the highlighted entry like a shell (`FileSelector::on_tab_complete`; completing a folder lists its contents). `BaseSelectorWidget::eventFilter` handles these keys on both the search box and the list: focus moves to the list after the first move, and the list would otherwise pass them on to the main window (Ctrl+D/U scrolled the document behind the popup, Tab ran `goto_portal`).
- `close_tab` command, aliased as `:q`, closes the current tab and shows its neighbour. Closing the last tab leaves an empty window. Upstream had `:q` as an alias for `close_window`, which quit the app when only one window was open. The command palette now ranks an exact name match first.
- Ctrl+Tab / Ctrl+Shift+Tab run `goto_next_tab` / `goto_prev_tab` (`<C-<tab>>`, `<C-S-<tab>>`). The user first asked for Shift+Tab, then changed it. Shift+Tab is back on upstream's `edit_portal`. On macOS, AppKit swallows the Ctrl+Tab key press for its own focus cycling, so neither `keyPressEvent` nor an accepted ShortcutOverride sees it. The `MainWidget` constructor therefore registers macOS-only QShortcuts (`Qt::META | Qt::Key_Tab` and `Qt::META | Qt::SHIFT | Qt::Key_Tab`; the Backtab form never matches). They forward a synthesized key event into `key_event()`, so keys.config stays authoritative. They do nothing while a popup is open. `InputHandler::get_event_key` also treats `"\u0019"`, the text macOS sends with Shift+Tab, as a special key, so `<S-<tab>>` bindings match.
- Tab bar look: Firefox-like tabs in the popup theme colors (selected tab outlined in the theme's border color), `ui_font` at `tab_bar_font_size` (default 14; vertical tab padding was cut by 1px at the user's request, making the bar about 41px). Each tab has its own always-visible close button (a `QToolButton` named `tab_close_button`, set with `setTabButton`), because the macOS style only shows Qt's built-in close buttons on hover. Middle-clicking a tab closes it. `update_tab_bar_style()` reruns on config reload and when the system appearance changes. When the tabs don't fit, the wheel or trackpad scrolls them (`TabBarMouseFilter`; QTabBar's own scroll arrows ignore the wheel on macOS), the current tab is scrolled into view, and painted chevron buttons (`tab_scroll_left_button`/`tab_scroll_right_button`) appear at the ends that have hidden tabs; clicking them scrolls. `update_tab_bar` sizes the bar from the last tab's rect because `sizeHint()` comes out a few pixels short with the stylesheet's tab margins.
- Tabs in the title bar (macOS, `macos_tabs_in_titlebar`, default on): the tab bar replaces the title bar next to the window buttons, like Firefox, and is then always shown, even with one or no tab (the user asked for that once the bars were unified). With the setting off it sits below the title bar and only appears with two or more tabs. `setTabsInTitlebar` in `macos_specific.mm` sets `NSWindowStyleMaskFullSizeContentView`, a transparent title bar and a hidden title, then (Electron's traffic-light technique) resizes the `NSTitlebarContainerView` to the bar's height and centers the close/minimize/zoom buttons in it; it returns where the buttons end so the tabs start after them. AppKit lays the title bar out again on resizes, full screen changes and title bar setting changes, sometimes in a later layout pass without a window notification, so the `YaviewTitlebarTabs` object attached to the window re-applies the layout after `NSWindowDidResize`/`DidEndLiveResize`/`DidExitFullScreen` and whenever the container's frame changes. On this macOS the title bar also blurs the content under it (`NSTitlebarBackgroundView` holding an `NSScrollPocket`, and a `CABackdropLayer` view inside `NSTitlebarView`); that blur covered the tabs until those views were hidden. `macos_specific.mm` is compiled without ARC: no `weak` properties, release what you alloc, and use `__block` for objects captured by long-lived blocks to avoid retain cycles. Clicks in the title bar area reach the Qt view (upstream's `macos_hide_titlebar` mode relies on that too). Dragging and double clicking empty parts of the bar call `startWindowDrag` / `performTitlebarDoubleClick` (which follows the system's double-click setting).
- Popup menus (`BaseSelectorWidget` in `ui.cpp`: command palette, table of contents, file browser, bookmarks, ...): centered at 60% of the window width and height by default. Configurable through `menu_screen_width_ratio`, `menu_screen_height_ratio` (the second, previously duplicated, width registration in `config.cpp` became the height), and `menu_screen_center_x` / `menu_screen_center_y` (the popup's center as a fraction of the window, clamped so it stays inside). Font: `font_size` (default 18; it only affects these popups) and `ui_font` (default `Monaspace Neon`, the user's WezTerm font; `get_ui_font_face_name` falls back to the bundled JetBrains Mono when the font is not installed, so the default stays monospaced).
- Popup theme: `ui_theme` is `auto` (default, follows the macOS light/dark appearance via `QStyleHints::colorScheme`), `dark`, `light`, or `custom` (the legacy `ui_background_color`/`ui_text_color`/`ui_selected_*` options). Dark and light each have `ui_{dark,light}_{background,text,selected_background,selected_text,border}_color`. The dark defaults come from the user's tmux status line (`~/.tmux.conf`: `#1a1410` background, `#ebdbb2` text, `#fe8019` selection, `#d65d0e` border); the light defaults are a matching gruvbox-light palette. `get_ui_colors()` in `utils.cpp` resolves the active theme. Popups draw a rounded border, a tinted search box, themed scrollbars, and no table grid lines (the grid cut through the selected row). Do not put padding on `QAbstractItemView::item`: Qt applied it only to the selected row and shifted its text.
- App icon: `resources/yaview-icon.png` is the user's 1254px source. For macOS it was refitted into `resources/yaview-icon-macos.png` (1024px), from which `resources/yaview.icns` is built with `iconutil`. macOS 26 and later put any icon whose outline does not match the system's rounded square onto a light gray plate in the Dock and Finder; the source, with its glow outside the square, got that plate. The fix renders that plate for the app with `NSWorkspace.shared.icon(forFile:)`, uses the plate's alpha as the exact system outline (824px at offset 100 on a 1024 canvas), fills it edge to edge with the artwork's body over the artwork's dark-green frame color, and drops everything outside it. Check new icons the same way: render the app's icon with `NSWorkspace` and look for the plate. `actool`/Icon Composer are not available (no full Xcode). The other icons are made from the unmodified source: `resources/yaview.ico` (Windows, 16 to 256px PNG entries), `resources/yaview-icon-linux.png` (256px) and the Android `android/res/drawable-*/icon.png`. The `.pro` file's `ICON`/`RC_ICONS` point at them.
- Mouse back/forward buttons run `prev_state` / `next_state`. On this Mac they never arrive as button presses: macOS turns them into swipe events (`NSEventTypeSwipe`, deltaX 1 for back and -1 for forward, each preceded by one with deltaX 0), so Qt's `XButton1`/`XButton2` handling in `mousePressEvent` never fired. `install_swipe_navigation_handler` in `macos_specific.mm` adds an `NSEvent` local monitor for swipes and calls `MainWidget::navigate_history` on the window under the cursor. Trackpad page swipes navigate the same way. Diagnosed with a plain AppKit window that logged every raw `NSEvent`: a Qt-level event log showed nothing for these buttons. Qt maps swipes to `QNativeGestureEvent` angles in a way that makes the deltaX 0 event look like "forward", so it isn't usable for this.

Synthetic mouse events don't reach a background window, and the test copy can't be activated while it shares a bundle id with the installed app.
- Testing without disturbing the user's open app: `build/local-macos/yaview.app/Contents/MacOS/yaview --new-instance --instance-name yaviewtest tutorial.pdf`, then drive it with `--instance-name yaviewtest --execute-command <command> [--execute-command-data <data>]`. AppleScript keystrokes go to the first running yaview, because both copies share a bundle id; post key events to the test process's PID instead. A small Swift helper using `CGEvent.postToPid` works for keys. Beware: `q` is bound to `quit`, so a dropped `:` keystroke followed by `q` quits the test instance.
- Test instances share the user's data folder unless isolated. When any instance quits gracefully (`quit`) it rewrites `auto.config` (window size and position) and `last_document_path.txt` (the tabs restored on the next launch); a test instance quitting after the user's app replaced the user's saved session twice. Isolate test instances like the memory tests do: `HOME` and `CFFIXED_USER_HOME` pointing at a throwaway folder move both `~/.config/yaview` and `~/Library/Application Support/yaview`, and a short private `TMPDIR` holds the instance socket; then a normal `quit` is harmless. Without isolation, a `quit` overwrites the user's session, and a `kill` (which saves nothing) leaks a shared memory segment (see below). Pass `--nofocus` so test windows don't take focus. `setconfig_<name>` changes made through `--execute-command` are not saved.
- `yaview --instance-name <name> --execute-command ...` starts a new yaview when no instance with that name is running, and that process can hang. Check `pgrep -lf MacOS/yaview` first. `--execute-command` takes a macro (commands separated by `;`); add `--wait-for-response` to wait until it ran (`noop`, `wait_for_search_to_finish` and `wait_for_renders_to_finish` are useful for syncing). Popups and opening a document never answer. The instance socket lives in `$TMPDIR/<instance name>`, and macOS limits socket paths to 104 characters, so a long `TMPDIR` breaks instance communication.
- macOS asks for permission when the app opens a file in a protected folder such as `~/Downloads` (the restored session includes one). The build is ad-hoc signed, so every reinstall counts as a new app and asks again. Until the user answers, the main thread blocks in `open()` and no window appears (`sample <pid>` shows it).
- Window screenshots: `screencapture -x -l <CGWindowID>` captures a window even when it is in the background. A Swift helper that reads `CGWindowListCopyWindowInfo` for the test PID finds the window id and bounds; `screencapture -x -R x,y,w,h` crops to a region.
- Fixed with the memory tests (2026-10-14), all also present upstream: the file browser's `QStringListModel`s and every popup's `MySortFilterProxyModel` had no Qt parent and leaked with each popup (now parented to the selector); `Document::detect_paper_name` never dropped the text page it extracts on the page-dimension worker thread (pages of another `fz_document` aren't cached by `get_stext_with_page_number`, so the caller owns them); and `Command::result_socket` was a raw `QLocalSocket*`, so a waiting command (`wait_for_renders_to_finish`, ...) that finished after its `--wait-for-response` client had gone crashed yaview with a use-after-free in `Command::on_result_computed` (now a `QPointer`).
- System V shared memory: yaview's single-instance guard (`RunGuard`) creates a System V shared memory segment per instance name and only removes it on a normal exit. macOS allows 32 segments system-wide (`kern.sysv.shmmni`). Killing many test instances with unique names used all 32 on 2026-10-14; after that every new yaview, including the user's, printed "Secondary application cannot attach to shared memory block" and exited at startup. Check with `ipcs -m -a`; segments with NATTCH 0 whose CPID no longer exists are orphans and can be removed with `ipcrm -m <id>`. Quit test instances with the `quit` command where possible (fine in an isolated home), and clean up after kills.
- Remote test runs: `.github/workflows/memory-tests.yml` builds yaview on a GitHub `macos-15` runner (caching the Qt SDK in `.local/qt` and MuPDF's build), runs the memory tests with `--window foreground`, and uploads the `memory-test-results` artifact. It runs only on `workflow_dispatch` (inputs `iterations` and `scenarios`) and on a weekly schedule (Sundays 06:00 UTC); the user asked for it never to run on pushes. The README's badge shows the latest run's result and date: GitHub's own workflow badge can't show a date, so the workflow's separate `badge` job (the only one with `contents: write`) force-pushes a shields.io endpoint file, `memory-tests.json`, to the orphan `badges` branch after every run that wasn't cancelled. The fork's other workflows (upstream's release builds) only run on `v*` tags and pull requests.
- Memory leak tests: `python3 tests/memory/memory_leak_tests.py` (see `tests/memory/README.md`). Each scenario runs an isolated, debuggable copy of the app (ad-hoc signed with `get-task-allow`, so `leaks` can save memory graphs), repeats user actions through `--execute-command`, and reports the leaks that are new since a baseline (`leaks --outputGraph` / `--diffFrom`) plus physical footprint growth. By default the test copies run as agent apps launched in the background through LaunchServices (own bundle id `info.yaview.yaview.memorytest`, App Nap off, `QT_MAC_DISABLE_FOREGROUND_APPLICATION_TRANSFORM=1` because Qt otherwise activates the app after launch), and every client message carries `--nofocus` (without it `focus_on_widget` in `main.cpp` raises and activates the window for each message). Before both fixes the tests took the user's keyboard focus constantly. Background windows are mostly covered and not redrawn, so rendering-related growth only shows with `--window foreground` or in CI: a foreground run showed graphics memory (IOSurface/IOAccelerator) growing about 8 MB per opening of the bookmark list, not reproduced in background mode and not yet investigated. A single window of this app has a physical footprint of about 2.5 GB at 3142x1761 points (page renders and GPU buffers); that is caching, not a leak.

## Working build commands

Use the local helper for this Mac:

```sh
cd /Users/yavo/code/sioyek
./scripts/build_local_macos.sh
```

To install a new build, first quit the running yaview app, then run:

```sh
./scripts/build_local_macos.sh --install
```

The helper builds MuPDF with `HAVE_GLUT=no`, uses qmake in a separate build directory with `release non_portable`, builds for the host architecture, copies configs/shaders/tutorial into the bundle, bundles Qt with `macdeployqt`, applies an ad hoc code signature, verifies it, and checks `--version`. Repeated builds are incremental.

When replacing an installed app, the helper refuses to proceed if yaview is running and saves the previous bundle under `.local/install-backups/<timestamp>/yaview.app`. User preferences and databases live outside the bundle.

Overrides:

- `MAKE_PARALLEL`: compilation jobs (default `8`).
- `YAVIEW_QT_ROOT`: alternate Qt SDK path (default `$repo/.local/qt/6.8.2/macos`).
- `YAVIEW_INSTALL_PATH`: alternate app destination (default `/Applications/yaview.app`).

## Compatibility fixes already in the helper

1. On `arm64`, adds `QMAKE_CXXFLAGS+=-include arm_acle.h`. Qt 6.8's `qyieldcpu.h` otherwise fails with newer Apple Clang because `__yield` lacks a declaration.
2. If the current SDK has no `AGL.framework`, removes the obsolete `-framework AGL` entry from the generated Makefile. Qt 6.8's link metadata still includes it, causing `ld: framework 'AGL' not found` on this SDK. This changes generated build output, not the Qt SDK or application sources.

The upstream `build_mac.sh` mutates the tracked `.pro` deployment target and deletes the `build/` directory. Prefer the local helper to retain incremental artifacts and these compatibility fixes. A `CMakeLists.txt` exists but was not used or validated in this setup.

In a restricted Codex sandbox, Qt tools may abort with `Incompatible processor ... neon` because hardware feature queries through `sysctl` are denied. They worked when the required build/launch commands ran with appropriate execution permissions. Do not diagnose this sandbox error as an actual missing CPU feature. Installing into `/Applications` also needs filesystem access outside a repo-only sandbox.

MuPDF objects were built with the host's default macOS 27 target, while the upstream qmake project targets macOS 15. Linker deployment-target warnings were nonfatal on this machine. Older macOS compatibility has not been verified; align deployment targets and rebuild MuPDF if it becomes a requirement.
