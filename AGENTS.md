Both `pdf_viewer/prefs.config` and the hardcoded defaults in `pdf_viewer/main.cpp` were changed. The user's own `~/.config/yaview/yaview.config` sets `search_url_s` to Kagi; their default browser is Waterfox.
- `o` opens the embedded in-app file browser rooted at the current document's folder (`open_document_embedded_from_current_path`). `Ctrl+o` opens it at `default_open_file_path`, and `Ctrl+Shift+o` opens the native macOS dialog. `FileSelector` in `pdf_viewer/ui.h` now starts in the home folder when given no path, instead of the process working directory (`/` for Finder launches).
- All visible search matches are highlighted, not just the current one (`should_highlight_unselected_search`, enabled in `prefs.config` and `config.cpp`).
- Cmd+= and Cmd+Shift+= zoom in, Cmd+- zooms out (`<D-=>`, `<D-+>`, `<D-->` next to the plain `+`/`-` bindings). Shift can't be combined with Cmd/Ctrl/Alt for symbol keys in keys.config; bind the shifted character instead (`<D-+>`, not `<D-S-=>`).
- The Left / Right arrow keys run `previous_page` / `next_page` (the user's request, 2026-10-17); upstream bound them to horizontal scrolling, which `h` / `l` still do. `next_page` / `previous_page` now show the page after / before the one at the top of the window, from its top (`MainWidget::turn_pages`); upstream moved by one page height, which kept any scroll misalignment. Presentation and two page modes still use upstream's `move_pages`.
- `Ctrl+D` / `Ctrl+U` run `screen_down` / `screen_up`, like PageDown/PageUp. On macOS `<C-...>` in keys.config is the physical Ctrl key and `<D-...>` is Cmd. The user asked for Ctrl, not Cmd.
- Tab bar: `MainWidget::tab_bar` (a `QTabBar`) lists `document_manager->get_tabs()`. Every opened document joins that list; `DocumentManager::add_tab_after` puts a newly opened document's tab right after the current one, like browsers (session restore keeps the saved order). The bar floats over the top edge of the view, like the status bar at the bottom, because mouse handling uses main-window coordinates with no offset correction; putting it in the layout would shift every click. `update_all_tab_bars()` must run after any `add_tab`/`remove_tab`.
- Tab bar structure and stacking: `tab_strip` (themed background; pressing it drags the window, double clicking zooms) under `tab_scroll_area` (a `QScrollArea` holding `tab_bar`, which is as wide as all its tabs). Stacking order: document view, tab strip, tab scroll area, popups, status bar. `set_current_widget` stacks popups directly under `status_label`, so the tab widgets stay under `status_label` and are never raised; raising them drew them over the command palette and table of contents. The text command line (`text_command_line_edit_container`, used for bookmark text, search and other typed input) sits at the window's top edge upstream; `update_tab_bar` moves it below the bar while the bar is shown, because the tab bar and the window buttons covered it (pressing `b` only showed a black band over the tab, so bookmarks seemed broken). Restored tabs from a previous session refresh the bar in `open_tabs`.
- In every list popup (table of contents `t`, command palette, file browser, ...), Ctrl+N / Ctrl+P move one line down / up and Ctrl+D / Ctrl+U one page down / up. Tab moves down and Shift+Tab up, except in the file browser, where Tab completes the typed path with the highlighted entry like a shell (`FileSelector::on_tab_complete`; completing a folder lists its contents). `BaseSelectorWidget::eventFilter` handles these keys on both the search box and the list: focus moves to the list after the first move, and the list would otherwise pass them on to the main window (Ctrl+D/U scrolled the document behind the popup, Tab ran `goto_portal`).

Other keys there still do nothing.
- Single configuration file (the user asked for one on 2026-10-17): `~/.config/yaview/yaview.config` on macOS and Linux (Windows: the app data folder, portable builds: next to the executable). It holds settings (`name value`), key bindings as `keymap <command> <keys>` lines and custom commands (`new_command`, `new_macro`); `keymap` is upstream's existing syntax, collected by `ConfigManager` into `ADDITIONAL_KEYMAPS` and appended after the default bindings by `parse_key_config_files`, so a keymap for an already bound key replaces it. `configure_paths` in `main.cpp` sets `user_config_paths` to just this file, the `InputHandler` gets no user key files, and `create_user_config_file` creates it with a two-line header on first start. Upstream's `prefs_user.config`/`keys_user.config` (looked up in several folders) are no longer read, and the `prefs_user`, `keys_user`, `prefs_user_all` and `keys_user_all` commands were replaced by `config`; `prefs` and `keys` still show the defaults (`prefs.config` and `keys.config` in the app bundle, not meant for editing). `auto.config` in the data folder stays: it is state yaview writes itself (window sizes and positions).
- `clear_document_marks` (command palette only, no key) deletes the marks of the current document from its file. `edit_mark` (no key; also Ctrl+R in the `show_marks` list) edits a mark's description, and `mark_to_bookmark` turns a mark into a bookmark at its location. Both derive from `MarkTextCommand`: the user picks the mark from a menu of the document's marks (`show_mark_picker`, a Generic requirement; a macro passes the letter, e.g. `edit_mark(a,'text')`), then types the text, prefilled with the description, in a `TextPromptWidget`: a prompt in the menu style, centered like the menus, for commands whose `uses_centered_text_prompt()` is true. `TextPromptWidget` positions its title and input itself in `place()`; with a `QVBoxLayout` they stayed unlaid (76x0) when its size was set from its own resizeEvent. The menu stylesheet is shared through `get_menu_stylesheet()`. `show_marks` puts the letter in its own column, sized to its contents (`fit_column_to_contents`). Commands started from the `:` command line set `Command::prompt_for_symbol`, so a letter requirement shows the prompt bar with the requirement's name and "(press a letter)" and no text field (`show_symbol_prompt`); key chords such as `ma` show no prompt, only the status bar hint.
- `clear_document_history` (command palette only, no key) deletes the `documents` rows behind the `open_prev_doc` (Shift+O) list, except for documents open in tabs. Those rows also hold each document's zoom and position, which is why open tabs keep theirs. Within the list, Delete or Cmd/Ctrl+Backspace removes one entry (upstream).
- `close_tab` command, aliased as `:q` and bound to Cmd+W (`<D-w>`), closes the current tab and shows its neighbour. Closing the last tab leaves an empty window. Upstream had `:q` as an alias for `close_window`, which quit the app when only one window was open. The command palette now ranks an exact name match first.
- Tabs whose file fails to open (moved or deleted, for example a restored session entry): the tab stays current, highlighted next to the "does not exist" message. `get_current_tab_index` falls back to `main_document_view->last_opened_file_path` when there is no `doc()`, the failed-open path in `open_document` refreshes the tab bar, and a `tabBarClicked` handler opens the highlighted tab when it isn't the shown document (Qt emits no `currentChanged` for it). `Command::requires_document()` defaults to true and such commands are skipped without a document, so `close_tab`, `goto_next_tab` and `goto_prev_tab` override it; before that, a failed tab left the window stuck (no key or click switched away).
- Ctrl+Tab / Ctrl+Shift+Tab run `goto_next_tab` / `goto_prev_tab` (`<C-<tab>>`, `<C-S-<tab>>`). The user first asked for Shift+Tab, then changed it. Shift+Tab is back on upstream's `edit_portal`. On macOS, AppKit swallows the Ctrl+Tab key press for its own focus cycling, so neither `keyPressEvent` nor an accepted ShortcutOverride sees it. The `MainWidget` constructor therefore registers macOS-only QShortcuts (`Qt::META | Qt::Key_Tab` and `Qt::META | Qt::SHIFT | Qt::Key_Tab`; the Backtab form never matches). They forward a synthesized key event into `key_event()`, so keys.config stays authoritative. They do nothing while a popup is open. `InputHandler::get_event_key` also treats `"\u0019"`, the text macOS sends with Shift+Tab, as a special key, so `<S-<tab>>` bindings match.
- Tab bar look: Firefox-like tabs in the popup theme colors (selected tab outlined in the theme's border color), `ui_font` at `tab_bar_font_size` (default 14; vertical tab padding was cut by 1px at the user's request, making the bar about 41px). Each tab has its own always-visible close button (a `QToolButton` named `tab_close_button`, set with `setTabButton`), because the macOS style only shows Qt's built-in close buttons on hover. Middle-clicking a tab closes it. `update_tab_bar_style()` reruns on config reload and when the system appearance changes. When the tabs don't fit, the wheel or trackpad scrolls them (`TabBarMouseFilter`; QTabBar's own scroll arrows ignore the wheel on macOS), the current tab is scrolled into view, and painted chevron buttons (`tab_scroll_left_button`/`tab_scroll_right_button`) appear at the ends that have hidden tabs; clicking them scrolls. `update_tab_bar` sizes the bar from the last tab's rect because `sizeHint()` comes out a few pixels short with the stylesheet's tab margins.
- Tabs in the title bar (macOS, `macos_tabs_in_titlebar`, default on): the tab bar replaces the title bar next to the window buttons, like Firefox, and is then always shown, even with one or no tab (the user asked for that once the bars were unified). With the setting off it sits below the title bar and only appears with two or more tabs. `setTabsInTitlebar` in `macos_specific.mm` sets `NSWindowStyleMaskFullSizeContentView`, a transparent title bar and a hidden title, then (Electron's traffic-light technique) resizes the `NSTitlebarContainerView` to the bar's height and centers the close/minimize/zoom buttons in it; it returns where the buttons end so the tabs start after them. The container is also narrowed to end 6 points after the buttons: it sits above the content view and took every click on the tabs for AppKit's window dragging (tab clicks and close buttons never reached Qt). Empty parts of the bar move and zoom the window through `TabBarMouseFilter` instead. With the content under the title bar, Qt also insets a window's contents by the title bar's height (safe area margins, 32 points); that moved the document view down while mouse handling uses window coordinates, so clicks and text selections landed lower on the page than the pointer. `MainWidget` and its central widget therefore turn off `Qt::WA_ContentsMarginsRespectsSafeArea`; the view must start at the window's origin. AppKit lays the title bar out again on resizes, full screen changes and title bar setting changes, sometimes in a later layout pass without a window notification, so the `YaviewTitlebarTabs` object attached to the window re-applies the layout after `NSWindowDidResize`/`DidEndLiveResize`/`DidExitFullScreen` and whenever the container's frame changes. On this macOS the title bar also blurs the content under it (`NSTitlebarBackgroundView` holding an `NSScrollPocket`, and a `CABackdropLayer` view inside `NSTitlebarView`); that blur covered the tabs until those views were hidden. `macos_specific.mm` is compiled without ARC: no `weak` properties, release what you alloc, and use `__block` for objects captured by long-lived blocks to avoid retain cycles. Clicks in the title bar area reach the Qt view (upstream's `macos_hide_titlebar` mode relies on that too). Dragging and double clicking empty parts of the bar call `startWindowDrag` / `performTitlebarDoubleClick` (which follows the system's double-click setting).
- Popup menus (`BaseSelectorWidget` in `ui.cpp`: command palette, table of contents, file browser, bookmarks, ...): centered at 60% of the window width and height by default. Configurable through `menu_screen_width_ratio`, `menu_screen_height_ratio` (the second, previously duplicated, width registration in `config.cpp` became the height), and `menu_screen_center_x` / `menu_screen_center_y` (the popup's center as a fraction of the window, clamped so it stays inside). Font: `font_size` (default 18; it only affects these popups) and `ui_font` (default `Monaspace Neon`, the user's WezTerm font; `get_ui_font_face_name` falls back to the bundled JetBrains Mono when the font is not installed, so the default stays monospaced).

- Mouse back/forward buttons run `prev_state` / `next_state`. On this Mac they never arrive as button presses: macOS turns them into swipe events (`NSEventTypeSwipe`, deltaX 1 for back and -1 for forward, each preceded by one with deltaX 0), so Qt's `XButton1`/`XButton2` handling in `mousePressEvent` never fired. `install_swipe_navigation_handler` in `macos_specific.mm` adds an `NSEvent` local monitor for swipes and calls `MainWidget::navigate_history` on the window under the cursor. Trackpad page swipes navigate the same way. Diagnosed with a plain AppKit window that logged every raw `NSEvent`: a Qt-level event log showed nothing for these buttons. Qt maps swipes to `QNativeGestureEvent` angles in a way that makes the deltaX 0 event look like "forward", so it isn't usable for this.

- Testing without disturbing the user's open app: `build/local-macos/yaview.app/Contents/MacOS/yaview --new-instance --instance-name yaviewtest test.pdf` (any PDF; `write_test_pdf` in `tests/memory/memory_leak_tests.py` writes a six-page one with a table of contents), then drive it with `--instance-name yaviewtest --execute-command <command> [--execute-command-data <data>]`. AppleScript keystrokes go to the first running yaview, because both copies share a bundle id; post key events to the test process's PID instead. A small Swift helper using `CGEvent.postToPid` works for keys. Beware: `q` is bound to `quit`, so a dropped `:` keystroke followed by `q` quits the test instance.
- Test instances share the user's data folder unless isolated. When any instance quits gracefully (`quit`) it rewrites `auto.config` (window size and position) and `last_document_path.txt` (the tabs restored on the next launch); a test instance quitting after the user's app replaced the user's saved session twice. Isolate test instances like the memory tests do: `HOME` and `CFFIXED_USER_HOME` pointing at a throwaway folder move both `~/.config/yaview` and `~/Library/Application Support/yaview`, and a short private `TMPDIR` holds the instance socket; then a normal `quit` is harmless. Without isolation, a `quit` overwrites the user's session, and a `kill` (which saves nothing) leaks a shared memory segment (see below). Pass `--nofocus` so test windows don't take focus. `setconfig_<name>` changes made through `--execute-command` are not saved.
- `yaview --instance-name <name> --execute-command ...` starts a new yaview when no instance with that name is running, and that process can hang. Check `pgrep -lf MacOS/yaview` first. `--execute-command` takes a macro (commands separated by `;`); add `--wait-for-response` to wait until it ran (`noop`, `wait_for_search_to_finish` and `wait_for_renders_to_finish` are useful for syncing). Popups and opening a document never answer. The instance socket lives in `$TMPDIR/<instance name>`, and macOS limits socket paths to 104 characters, so a long `TMPDIR` breaks instance communication ("Cannot start IPC server"). Qt first creates the socket in a temporary folder next to that path, so keep `TMPDIR` well under 80 characters. A command message that arrives while the window shows no document goes through the startup restore in `handle_args`: it re-adds the saved session's tabs and opens its first file, whatever the command is. Use keys (posted to the PID) to test commands in that state.
- macOS asks for permission when the app opens a file in a protected folder such as `~/Downloads`, including files reopened by session restore. The build is ad-hoc signed, so every reinstall counts as a new app and asks again. Until the user answers, the main thread blocks in `open()` and no window appears (`sample <pid>` shows it).
- Window screenshots: `screencapture -x -l <CGWindowID>` captures a window even when it is in the background. A Swift helper that reads `CGWindowListCopyWindowInfo` for the test PID finds the window id and bounds; `screencapture -x -R x,y,w,h` crops to a region.
- Fixed with the memory tests (2026-10-14), all also present upstream: the file browser's `QStringListModel`s and every popup's `MySortFilterProxyModel` had no Qt parent and leaked with each popup (now parented to the selector); `Document::detect_paper_name` never dropped the text page it extracts on the page-dimension worker thread (pages of another `fz_document` aren't cached by `get_stext_with_page_number`, so the caller owns them); and `Command::result_socket` was a raw `QLocalSocket*`, so a waiting command (`wait_for_renders_to_finish`, ...) that finished after its `--wait-for-response` client had gone crashed yaview with a use-after-free in `Command::on_result_computed` (now a `QPointer`).
- System V shared memory: yaview's single-instance guard (`RunGuard`) creates a System V shared memory segment per instance name and only removes it on a normal exit. macOS allows 32 segments system-wide (`kern.sysv.shmmni`). Killing many test instances with unique names used all 32 on 2026-10-14; after that every new yaview, including the user's, printed "Secondary application cannot attach to shared memory block" and exited at startup. Check with `ipcs -m -a`; segments with NATTCH 0 whose CPID no longer exists are orphans and can be removed with `ipcrm -m <id>`. Quit test instances with the `quit` command where possible (fine in an isolated home), and clean up after kills.
- Remote test runs: `.github/workflows/memory-tests.yml` builds yaview on a GitHub `macos-15` runner (caching the Qt SDK in `.local/qt` and MuPDF's build), runs the memory tests with `--window foreground`, and uploads the `memory-test-results` artifact. It runs only on `workflow_dispatch` (inputs `iterations` and `scenarios`) and on a weekly schedule (Sundays 06:00 UTC); the user asked for it never to run on pushes, and for the weekly run to test only when the app's source code changed (documentation and other files don't count). Manual runs always test. The README's badge (right-aligned, at the user's request) shows the latest run's result, how many days ago it ran and how many commits `main` has gained since the tested commit, e.g. `passing · 3 days ago · 19 commits behind` (`today`, `1 day ago`; `latest commit` when no commits). GitHub's own workflow badge can't show any of that, so `.github/scripts/memory-tests-badge.sh` force-pushes a shields.io endpoint file, `memory-tests.json`, to the orphan `badges` branch (always a single commit), with the run's data in `memory-tests-result`, `memory-tests-date` and `memory-tests-commit` (the tested commit). The workflow's separate `badge` job (the only one with `contents: write`) runs it after every run whose tests ran and weren't cancelled; `.github/workflows/memory-tests-badge.yml` runs it on every push to `main` and daily (00:05 UTC) to recount the days and commits, without running any tests or changing the recorded result and date. The script only pushes when something changed, and leaves the count out when the tested commit is no longer in the history. Releases: `.github/workflows/release.yml` runs only when started by hand (the user decides when to release). It builds the latest commit on `main` (whatever branch the run was started from) on a `macos-15` runner with the same Qt/MuPDF caches, zips `yaview.app` (Apple silicon, ad-hoc signed, not notarized, so the notes tell users to clear the quarantine attribute), and a separate `contents: write` job creates the release and its tag at that commit. The `version` input sets the tag; empty means `vYYYY.MM.DD` (`.2`, `.3`, ... for more releases that day); an existing tag fails the run. Notes list the commits since the previous release. Upstream's release workflows (`build_and_release.yml`, `preview_release.yml`: retired `ubuntu-20.04` runner, archived release actions, Windows/Linux builds) were removed on 2026-10-17. The fork still carries upstream's old tags (`v1.x`, `v2.0.0`) but had no releases before that. The app still reports the hardcoded version `2.0.0` (see below), not the release tag.
- Removed when annotations moved into the PDF file (2026-10-17, see "Annotation storage in the PDF file" below): the freehand drawing and scratchpad features (`ScratchPad`, `FreehandDrawing`, pen/tablet drawing, `TouchDrawControls`, the drawing shaders and icons), global (uppercase) marks at the user's request, `clear_all_marks`, the content checksum (`checksum.cpp`), the `.yaview.annotations`/`.drawings`/`.scratchpad`/`.extras` side files, `import`/`export` (JSON), `embed_annotations`, `import_annotations`, `write_annotations_file`, `load_annotations_file`, `scan_new_files`, `--shared-database-path`, and the settings `shared_database_path`, `annotations_directory`, `lighten_colors_when_embedding_annotations`, `simplify_freehand_drawings`, `scan_path`. The touch menu's hint button now runs `toggle_rect_hints` (it toggled the scratchpad). List popups got Ctrl+R to edit the highlighted entry (their edit action was only on Insert, which Mac keyboards lack).
- Memory leak tests: `python3 tests/memory/memory_leak_tests.py` (see `tests/memory/README.md`). Each scenario runs an isolated, debuggable copy of the app (ad-hoc signed with `get-task-allow`, so `leaks` can save memory graphs), repeats user actions through `--execute-command`, and reports the leaks that are new since a baseline (`leaks --outputGraph` / `--diffFrom`) plus physical footprint growth. By default the test copies run as agent apps launched in the background through LaunchServices (own bundle id `info.yaview.yaview.memorytest`, App Nap off, `QT_MAC_DISABLE_FOREGROUND_APPLICATION_TRANSFORM=1` because Qt otherwise activates the app after launch), and every client message carries `--nofocus` (without it `focus_on_widget` in `main.cpp` raises and activates the window for each message). Before both fixes the tests took the user's keyboard focus constantly. Background windows are mostly covered and not redrawn, so rendering-related growth only shows with `--window foreground` or in CI: a foreground run showed graphics memory (IOSurface/IOAccelerator) growing about 8 MB per opening of the bookmark list, not reproduced in background mode and not yet investigated. A single window of this app has a physical footprint of about 2.5 GB at 3142x1761 points (page renders and GPU buffers); that is caching, not a leak.

## Annotation storage in the PDF file

Since 2026-10-17 (the user's request) everything the user adds to a document lives in the PDF file itself, so other readers see it and nothing depends on a database. The code is `pdf_viewer/document_annotations.cpp`; `Document` keeps the in-memory copies.

- Highlight: a `Highlight` annotation, `Underline` for an uppercase type, `StrikeOut` for `_`. `/QuadPoints` are its rects, `/C` the type's color (read back as the nearest `highlight_color_<letter>`), `/Contents` its note. The highlighted text is not stored; `get_highlight_text` extracts it when needed.
- Bookmark: a `Text` annotation (a marker; `b` puts it at the left margin of the page, keyboard-made portals go at the right margin so the two don't overlap), a `FreeText` annotation for a freetext bookmark (rect, font size and color in `/DA`), a `Square` for a box bookmark (description `#<type> ...`). The text is `/Contents`.
- Portal: a `Link` annotation marked `/Yaview /Portal`, with a `GoTo` action to `[page /XYZ x y zoom]` in the same file or `GoToR` with a relative file specification for another file. The destination file may be closed, so `PortalViewState` keeps the page and a position in PDF user space (origin bottom left); `book_state(Document*)` and `Document::pdf_space_to_page_pos` convert it.
- Mark: an entry `<< /D [page /XYZ x y zoom] /Title (description) >>` in `/Yaview << /Marks << ... >> >>` in the document catalog, keyed by the letter. Keys are case-sensitive, so `a` and `A` are two marks of the document; there are no global marks. The `/` mark a search sets is session state and never written. Named destinations, the standard feature, were rejected: MuPDF and pdf.js ignore a catalog `/Dests` when a `/Names` tree exists, and adding to the tree means rewriting it.
- Ownership: every `Highlight`, `Underline`, `StrikeOut`, `Text`, `FreeText` and `Square` annotation in a file is a yaview annotation, including ones other programs made. `PdfRenderer` skips those subtypes (`run_page_without_yaview_annotations`, on both the whole-page and the sliced render path) and yaview draws them itself; `render_pdf_annotations` only governs the other kinds.
- Identity: an annotation is identified by its PDF object number (`Annotation::pdf_object`, 0 until written). There are no uuids and no content checksum; documents are identified by path everywhere.
- Reading: annotations are read in `Document::load_page_dimensions`' background thread, which loads every page anyway (`read_page_annotations` and `read_marks` read the raw dictionaries, without appearance synthesis). `set_annotations` merges in annotations added while the thread ran.
- Writing: each change is written immediately and saved by `save_annotations` with an incremental save (`pdf_save_document` with `do_incremental`), which appends after the original bytes and never rewrites them; `pdf_update_annot` writes appearance streams for other readers. MuPDF assumes one incremental save per loaded document: every save truncates the file to its original size and rewrites the session's whole section, so `save_annotations` resets `startxref` to the original value first (otherwise the trailer's `/Prev` points at the previous save's xref, which is gone, and readers report a broken xref). A save updates `last_update_time` so the reload-on-file-change check doesn't fire.
- Only PDF documents can hold annotations (`can_annotate`; `ensure_annotatable` shows a status message for EPUB and other formats).
- The database `yaview.db` (`database.cpp`) only keeps reader state, in the `documents` table keyed by path: zoom, offsets and last access (the Shift+O list), the detected paper name, and the EPUB layout size, which `open_document_with_file_name` applies in every thread. Upstream's `local.db`, `shared.db` and `test.db` are not read and their annotations were not migrated. There are no side files next to documents.
- Highlight lists (`gh`, `gH`) show each highlight as `[type] text` on one line, cut to `highlight_list_text_length` (default 100) characters; `gH` adds the file name, both show the page. Highlight texts are extracted lazily, so `gh` calls `load_highlight_texts` first.
- Bookmark markers are drawn as hanging tags (`render_bookmark_tag`, a `QPainterPath`) in one of six muted colors picked by the bookmark's object number; the ornate `B` icon was removed at the user's request.
- `gB` and `gH` (`goto_bookmark_g`, `goto_highlight_g`) list the bookmarks or highlights of the open documents (the tabs) and the `recent_documents_in_annotation_lists` (default 20) most recently opened ones, ordered by `last_access_time` in `documents` (`get_open_and_recent_document_paths`), with each entry's file name and page. Documents that aren't loaded are read from their files on demand (`read_annotations_from_file`); deleting or editing (`edit_bookmark_text`, Ctrl+R) an entry loads the document (`get_loaded_document`) and saves its file.
- To check a change, run an isolated test instance (see the testing notes) and inspect the file with `mupdf/build/release/mutool show <file> <object number>` and `mutool clean <file> out.pdf`, which must not report a repair.

## Working build commands

From the repository root:

```sh
./scripts/build_local_macos.sh
```

To install a new build, first quit the running yaview app, then run:

```sh
./scripts/build_local_macos.sh --install
```

The helper builds MuPDF with `HAVE_GLUT=no`, uses qmake in a separate build directory with `release non_portable`, builds for the host architecture, copies configs/shaders into the bundle, bundles Qt with `macdeployqt`, applies an ad hoc code signature, verifies it, and checks `--version`. Repeated builds are incremental.

When replacing an installed app, the helper refuses to proceed if yaview is running and saves the previous bundle under `.local/install-backups/<timestamp>/yaview.app`. User preferences and databases live outside the bundle.

Overrides:

- `MAKE_PARALLEL`: compilation jobs (default `8`).
- `YAVIEW_QT_ROOT`: alternate Qt SDK path (default `$repo/.local/qt/6.8.2/macos`).
- `YAVIEW_INSTALL_PATH`: alternate app destination (default `/Applications/yaview.app`).

## Toolchain and SDK recovery

Verified on Apple Silicon `arm64`, macOS `27.0.1`, Apple Clang `21.0.0`, macOS SDK `27.0`, with the Command Line Tools only (no full Xcode installation).

Qt `6.8.2` is installed locally, using `aqtinstall 3.3.0` in `.local/venv`. Required additional Qt modules are `qtspeech`, `qtshadertools`, and `qtmultimedia`; the latter is a dependency of the speech module. The installer also installs the standard base archives, including Qt Declarative, SVG, and Tools.

A `qmake` already on PATH may belong to another Qt (Qt 5 is unsuitable for this development branch). The helper calls the local Qt 6 SDK's tools by full path, runs with a PATH of only that SDK and the system folders, and clears inherited Qt plugin/QML paths. Do not replace or uninstall the user's other Qt installations.

If the local SDK or virtualenv is missing, recreate it with:

```sh
mkdir -p .local
python3 -m venv .local/venv
.local/venv/bin/python -m pip install 'aqtinstall==3.3.0'
.local/venv/bin/python -m aqt install-qt mac desktop 6.8.2 clang_64 \
  -b https://ftp.fau.de/qtproject --timeout 60 \
  -m qtspeech qtshadertools qtmultimedia -O .local/qt
```

Qt's `clang_64` package contains Apple Silicon support; the helper builds for the host architecture (`uname -m`). The default Qt mirror selection failed with connection/certificate errors during setup; the explicit FAU HTTPS mirror above succeeded. Keep certificate and archive integrity checks enabled.

## Compatibility fixes already in the helper

1. On `arm64`, adds `QMAKE_CXXFLAGS+=-include arm_acle.h`. Qt 6.8's `qyieldcpu.h` otherwise fails with newer Apple Clang because `__yield` lacks a declaration.
2. If the current SDK has no `AGL.framework`, removes the obsolete `-framework AGL` entry from the generated Makefile. Qt 6.8's link metadata still includes it, causing `ld: framework 'AGL' not found` on this SDK. This changes generated build output, not the Qt SDK or application sources.

The upstream `scripts/build_mac.sh` (moved there from the repository root with the other platform build scripts on 2026-10-17) mutates the tracked `.pro` deployment target and deletes the `build/` directory. Prefer the local helper to retain incremental artifacts and these compatibility fixes. A `CMakeLists.txt` exists but was not used or validated in this setup.

In a restricted Codex sandbox, Qt tools may abort with `Incompatible processor ... neon` because hardware feature queries through `sysctl` are denied. They worked when the required build/launch commands ran with appropriate execution permissions. Do not diagnose this sandbox error as an actual missing CPU feature. Installing into `/Applications` also needs filesystem access outside a repo-only sandbox.

MuPDF objects were built with the host's default macOS 27 target, while the upstream qmake project targets macOS 15. Linker deployment-target warnings were nonfatal on this machine. Older macOS compatibility has not been verified; align deployment targets and rebuild MuPDF if it becomes a requirement.
